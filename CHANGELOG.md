# Changelog

Detailed build history, moved out of the main README so that stays a submission-facing document rather than a build diary. Full commit messages carry the same detail — this is the summary.

- **Stage 1** — repo scaffold, `docs/blueprint.md`, and the browser-based extraction demo (`demo/`)
- **Stage 2** — Android project skeleton: manifest with `ShareReceiverActivity` registered as a Share target (zero declared permissions), Room schema (`VoiceNote` + `Packet`), Compose UI, `PacketExtractor` interface with a stub implementation. Verified via a standalone Kotlin 2.0.21 compile pass (no Android classpath available in the environment that built this); caught and fixed one real bug — a doc comment containing `audio/*` had silently opened an unclosed nested block comment (Kotlin nests `/* */`, unlike Java).
- **Stage 3** — on-device model integration: `DeviceTierDetector` (real RAM check via `ActivityManager`, cached), `AudioPreprocessor.chunkBoundaries` (pulled out, compiled standalone, run through 6 test cases before being copied in), and the first MediaPipe LLM Inference wiring for both device tiers. Surfaced two open questions at the time: the exact audio-ingestion API call was unconfirmed, and Android/ML Kit have no public API for transcribing an already-recorded audio file (both are built for live mic dictation).
- **Stage 4** — `OSActionBridge`: real `ACTION_INSERT` (opens the calendar app's own new-event screen, no calendar permission needed) and `ACTION_SEND` + chooser (reminder handoff and reply handoff, same mechanism for both) intents, with a clipboard-copy fallback if nothing on the device can handle either.
- **Stage 5** — swipe-to-dismiss (Material3 `SwipeToDismissBox`, alongside the original × button), an empty state once every card in a result is dismissed, a per-package `README.md`, and a real correctness fix: `ShareReceiverActivity` had been silently substituting the sample transcript when a share intent carried no readable audio URI, which would have shown a stranger's canned example instead of an honest error. Now reports a genuine error state instead.
- **Fix — fallback visibility** — running the Stage 3–5 build on a real device surfaced that the device-tier badge (a real capability check) and the extraction output (possibly the Stage 2 stub, if no model file is on the device) had no visual distinction — a real "High-tier device · Gemma-3n E2B" badge next to a fixed, unchanging example reads as a working demo, not a fallback. `PacketExtractorFactory` now returns whether it's using a real model, surfaced via `ModelStatusBanner`.
- **Fix — MediaPipe audio API correction** — live web research (prompted directly by trying to get a real extraction running) corrected a guessed API call: `session.addAudioClip(pcm)` doesn't exist. The confirmed call, per Google's official Android LLM Inference guide, is `session.addAudio(audioData: ByteArray)`, gated behind `AudioModelOptions` (engine options) and `GraphOptions.setEnableAudioModality(true)` (session options) — neither of which existed in the code before, not just the method name. The expected byte format (PCM16, 16kHz, mono) is now implemented via three pure functions (resample, downmix, byte serialization), each compiled and run through 8 test cases before being copied in. That same research surfaced that the commonly-linked `gemma-3n-E2B-it-int4.task` "preview" checkpoint is text-and-vision only — the audio-capable release is a newer `.litertlm`-format checkpoint — and that Gemma 3 1B (the budget-tier model) likely has no audio-capable checkpoint at all, a narrower, more fundamental version of the budget-tier problem than originally scoped.
- **iQOO Hackathon 2026 repositioning** — see the root `README.md` and `SUBMISSION.md`. The Android app (Track A) is the primary submission per the hackathon's own rubric (phone-first execution and on-device AI are explicitly weighted, cloud-API and web-only builds are explicitly penalized); the browser demo (Track B) is repositioned as validation evidence for the extraction schema, not a competing demo path.
